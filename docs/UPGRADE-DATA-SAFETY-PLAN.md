# 应用升级与用户数据保护计划

日期：2026-11-17（Asia/Shanghai）。状态：待实施；本文是实施计划，不代表迁移、自动备份或跨版本升级测试已经完成。

## 目标与范围

用户从 GitHub Release 下载新版本，退出旧应用并替换 `.app` 后，应能继续查看、播放、导出原有会议，保留录音、转写、摘要、存储目录配置和偏好设置。遇到格式不支持、文件损坏或目录不可访问时，应保留原文件，并说明原因和恢复方式。

本计划覆盖数据格式兼容、迁移前备份、失败恢复、应用与只读 CLI 的一致性，以及发布前验证。自动下载更新、云备份、Developer ID 签名和公证另行规划。

## 当前实现与缺口

| 数据 | 当前存储位置或读取入口 | 升级相关行为与缺口 |
| --- | --- | --- |
| 存储设置 | `~/Library/Application Support/Meeting Intelligence/settings.json`；`StorageSettingsStore` | 应用包外保存；尚无显式格式版本，解码失败会报错。 |
| 录音及元数据 | 默认 `Recordings/<UUID>/`；`RecordingStore` | 音频与 `recording.json` 在应用包外；元数据只接受 `schemaVersion = 1`。 |
| 转写和摘要 | 默认 `Transcripts/`；`TranscriptDocument` | 摘要在转写 JSON 内；只接受 `schemaVersion = 1`。已有会议可通过 `transcriptPath` 指向其他位置。 |
| 自定义目录 | 存储设置中的当前目录、`audioHistoryDirectories` 及会议文件引用 | 需要覆盖外置磁盘、历史录音目录及旧转写文件，不能只扫描默认目录。 |
| 偏好设置 | `UserDefaults.standard`；`AppModel` | 依赖稳定的应用身份和设置键；迁移时不能用默认值覆盖已有偏好。 |
| API Key | macOS Keychain；`TranscriptionCredentials`、`SummaryCredentials` | 不在应用包内；当前临时签名可能需要用户重新授权访问。授权失败不能当作凭据不存在。 |
| CLI | `MeetingReadRepository` | 只读校验格式，目前只支持版本 1；不能由 CLI 隐式执行迁移或修复。 |

Release ZIP 由 `scripts/package-release.sh` 生成，包含应用、README 和 LICENSE，不包含用户数据。当前 Bundle ID 是 `local.meeting-intelligence.app`。替换应用包通常会保留数据，但还没有完整的数据迁移、备份恢复和跨版本安装验证体系。

## 必须保持的约束

- 保持 Bundle ID、默认数据目录、Keychain service/account 标识稳定。确需调整时，单独提供迁移及兼容方案。
- 不因读取失败删除文件、重建空资料库或静默回退到默认存储目录；新装且没有配置文件的情况除外。
- 应用版本、构建号与磁盘格式版本分开管理。普通版本升级不应为了更新版本号而重写所有会议文件。
- 同一磁盘格式下新增字段须能读取旧文件，默认值通过明确的解码逻辑保证；不能只依赖 Swift 属性初始值。
- 读取比当前程序更新的格式时，在修改文件、恢复录音状态或启动后台任务之前停止写入。提示使用兼容版本打开。
- 迁移在本地完成，不调用转写或摘要服务，不重新生成已有内容，不把音频、转写或密钥写入日志与 CI 产物。

## 第一阶段：固定兼容契约与旧数据样本

优先完成这一阶段，为现有版本提供可验证的升级保障，不引入没有实际用途的版本 2。

1. 梳理 `Recording`、`TranscriptDocument`、`StorageSettings` 及嵌套类型的必填字段、可选字段、枚举值和默认值，形成格式兼容表。
2. 用真实历史格式结构制作合成 fixtures，覆盖最早可支持版本、当前版本、缺少后续新增可选字段、已有摘要、未完成录音及历史自定义目录。样本不得包含真实会议数据。
3. 在 `MeetingCore` 统一版本检查和错误分类。先检查原始格式版本，再解码对应类型；区分不支持的格式、损坏文件、无权限和磁盘离线，避免统称为“没有数据”。
4. 明确设置文件的版本演进策略：无版本字段按已知旧格式读取；只有需要改变格式时才引入显式版本。缺失字段与无效字段分别处理，不能以默认值掩盖损坏。
5. 一份会议损坏时，允许列出其他可读会议，并单独提示问题记录；任何失败项都不自动覆盖。应用和 CLI 使用一致的格式规则，CLI 保持只读并返回明确状态。
6. 为同格式升级约定读写兼容范围。旧程序重新保存时可能丢弃未知字段，需选择保留未知字段或提升格式版本并阻止不兼容写入，不能只验证“新版能读旧版”。

交付物：兼容契约、合成 fixtures、兼容读取及错误隔离实现、对应自动化测试。

## 第二阶段：迁移前备份与恢复入口

在首次需要修改磁盘格式之前完成，备份失败时不开始迁移。

1. 发现数据范围：读取设置、当前与历史音频根目录、每份会议实际引用的转写路径。对重复路径去重；不任意递归扫描用户磁盘，不跟随链接写入范围外文件。
2. 迁移备份默认放在应用数据目录下独立的 `Backups/<migration-id>/`，不得混入录音列表。记录迁移 ID、来源/目标格式、应用版本、原路径、相对备份路径、文件大小及 SHA-256。
3. 迁移前保存将要修改的设置、会议元数据和转写/摘要原始字节，以及涉及变更的非敏感偏好设置。备份完成后逐项校验；不要将解码再编码后的内容冒充原始备份。
4. 首期迁移不修改音频，只校验音频路径、大小及必要的内容校验信息。明确说明这种备份用于恢复迁移涉及的元数据，不是完整灾备；用户完整备份须额外复制所有音频与自定义目录。
5. Keychain 密钥不导出到备份或日志。凭据访问被拒绝时提供显式重新授权入口，保留现有凭据。
6. 显示备份位置、占用空间与恢复方法。空间不足、历史目录离线或权限不足时，保留当前文件，给出重试入口，不将缺失数据从设置中移除。
7. 恢复前停止所有写入并保存当前状态；验证备份与目标路径，在临时位置校验恢复内容后再替换。恢复入口需防止覆盖备份之后新增或编辑的会议；先报告冲突并由用户选择，不能直接整库回滚。
8. 默认不自动清理迁移备份。后续如增加保留策略，必须先提供可见的管理入口，不能删除唯一可用恢复副本。

交付物：可校验的备份清单、备份与恢复服务、错误提示和恢复说明。

## 第三阶段：按实际需要增加可恢复迁移

只有出现必须改变格式的需求时才新增迁移步骤。版本 1 保持原样可读，不进行空迁移。

1. 通过显式的 `vN -> vN+1` 步骤迁移，每步定义输入、输出、校验和兼容范围。迁移入口放在应用的数据服务中，在录音中断恢复和后台任务写入之前执行。
2. 使用互斥机制协调应用实例及其他写入者。迁移期间禁止录音、转写、摘要提交、删除和设置变更；只读 CLI 若无法取得一致快照，应返回“迁移中”并保持原文件不变。
3. 先检查整次迁移涉及的数据和写权限，确认已校验的备份可用，再在目标文件所在卷的临时文件中生成结果，并验证格式、会议 ID、引用关系、时间戳和摘要内容。
4. 单文件通过同卷原子替换提交；多个文件、多个目录或卷之间不存在整体原子替换保证，因此使用持久化迁移日志记录准备、逐项提交和完成状态。
5. 在每个提交边界支持中断恢复。启动时先检查日志，校验已提交内容，按既定规则继续或从备份恢复；重复启动不得重复转换、复制会议或覆盖原备份。
6. 提交完成后重新加载并核对记录数、会议 ID、音频引用、转写段落和摘要。迁移不得改变音频字节，不能为了校验调用付费服务。
7. 回滚必须同时恢复一致的元数据集合，避免出现新旧格式混用；回滚失败时保留日志、备份和现场，暂停写入并提供可定位的恢复提示。
8. 磁盘格式升级可能使旧版应用无法打开。首次破坏兼容的迁移前说明影响和备份位置；文档不得承诺安装旧应用就能完成降级，降级应使用对应备份副本并处理新增数据冲突。

交付物：迁移调度、互斥和日志、首个实际迁移步骤、中断恢复及回滚验证。

## 第四阶段：升级体验与发布检查

- 中英文 README 同步说明升级方式、数据位置、自定义目录备份方式、Keychain 重新授权及格式降级限制。
- 应用展示区分明确的错误：数据较新、文件损坏、外置磁盘离线、无权限、备份空间不足、迁移中断。提供定位文件、重试或恢复入口。
- 在 `AGENTS.md` 增加持久化变更要求：修改磁盘结构时必须更新兼容契约、fixtures、迁移/备份方案和发布说明。
- 将兼容与恢复测试接入现有 `scripts/test.sh` 和 CI；避免为每次提交增加重复的完整双架构打包。发布工作流继续验证两种架构。
- Release notes 对涉及磁盘格式变化的版本列出来源/目标格式、备份位置、旧版本兼容范围及恢复步骤。
- 用上一个已发布版本和候选 Release 包做一次实际替换升级检查，记录两个包的 tag/commit、架构、系统版本和结果。测试只使用合成会议，不读取真实用户资料库。

## 验收矩阵

| 场景 | 必须满足的结果 |
| --- | --- |
| 替换新版 `.app`，格式未变 | 原会议数量及 ID 一致，音频可播放，转写/摘要可查看并导出，目录与偏好保留；不因升级重写全部文件。 |
| 旧文件缺少新增字段 | 使用约定默认值正常读取，已存在字段不丢失。 |
| 自定义与历史目录、旧转写路径 | 全部可访问数据仍可发现；不能只查默认目录或当前转写目录。 |
| 外置盘离线、权限不足、单条 JSON 损坏 | 清晰报告受影响记录，保留文件和配置，其余记录可访问；不静默清空列表。 |
| 遇到未来格式或尝试降级 | 在写入前拒绝不兼容操作，原文件校验值不变，并说明恢复/兼容要求。 |
| 备份磁盘不足或校验失败 | 不提交迁移，不修改原文件，允许修复环境后重试。 |
| 迁移在任一提交边界被中断 | 重启后能确定性继续或回滚，重复运行无重复会议，无丢失或半完成格式。 |
| 迁移时打开另一实例或 CLI | 无并发写入；CLI 保持只读，返回一致快照或明确的忙碌状态。 |
| 恢复备份时已有新数据 | 先检测冲突并保留新数据，不静默覆盖。 |
| Keychain 授权拒绝 | 不删除凭据、不清空设置；重新授权后可继续使用。 |
| Apple Silicon 与 Intel 发布包 | 使用相同的数据格式规则，均通过合成数据升级与核心功能检查。 |

自动化测试使用临时目录、合成音频、可注入的文件系统故障及模拟凭据存储。真实 macOS 权限弹窗与跨包签名访问行为另做手工验证，不用 mock 结果代替系统验证。

## 实施顺序与完成判定

- [ ] P0：完成第一阶段，固定现有格式兼容契约及回归样本，验证普通应用替换的数据保留行为。
- [ ] P1：完成第二阶段，具备可校验备份与不覆盖新增数据的恢复能力。
- [ ] P1：在首个实际格式变更前完成第三阶段；未通过故障恢复测试，不发布破坏兼容的格式变化。
- [ ] P1：完成第四阶段的用户说明、开发约束与 Release 验收记录。

只有代码、兼容/故障测试、文档及实际升级检查均完成后，才将对应阶段标记为完成。仅安装包可启动、JSON 能解码或文件仍存在，都不足以证明升级后数据完整可用。
